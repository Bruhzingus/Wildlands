# Phase 13 implementation and verification

Implemented on 2026-10-19. Automatic graphics is the selected default for both integrated-graphics laptops and gaming PCs. Target-device GPU measurements remain distinct from software-renderer QA.

PHASE: 13 — Reliability, performance and memory tests

What changed: Added Automatic / Low / Balanced / High graphics, independent 50/75/100% resolution, and 35–100% effect density controls to the existing title/pause settings. Preferences are sanitized and persist alongside camera/audio/comfort settings. Automatic selection starts from CPU/memory hints and adjusts only after sustained native-captured active frame intervals, with bounded windows, warmup and hysteresis. It responds to sustained very slow frames and ignores suspension-sized gaps. Manual selection stops automatic adjustments. Pixel density is capped separately for each preset. Low graphics hides only noncolliding bushes/flowers. Effect density samples decorative impact puffs and dust; actual projectiles, pickups, windups and psychic waves keep their complete coverage. System reduced-motion changes now propagate to effects live.

Development diagnostics expose bounded recent frame/simulation/presentation/render timing, mesh/active mesh/geometry/material/texture/sprite-manager/transform/light counts, actors/projectiles/drops, pooled effects, audio and optional Chrome heap data through `inspectPerformance()`. Collection is enabled only in development with `?dev=1`; it has no storage, network, listeners or timers. Removed a per-frame camera Vector3 allocation and stopped rebuilding the interaction prompt every frame when the same discovery remains nearby. Existing bounded substeps remain: at most 80ms accepted per rendered frame, split into updates no larger than 20ms, with action taps consumed once and hit-pause buffering preserved.

Added a reproducible headless long-session profiler and browser tests for live/persisted graphics controls, blocked storage, ten actual start/pause/restart cycles, above-budget crowded rendering, projectile/FX limits and unavailable artwork fallback. Review also fixed Quickened applying after the opening eight enemies had already spawned: typed run configuration now enters Simulation before those actors are created. This preserves default Simulation behavior and ensures selected rules apply from the first frame.

Changed files: `src/game/graphics.ts`, `src/game/performance.ts`, `src/game/settings.ts`, `src/game/Game.ts`, `src/game/Simulation.ts`, `src/game/render/World.ts`, `src/game/render/Effects.ts`, `src/ui/UI.ts`, `src/style.css`, `tests/graphics.test.ts`, `tests/challenges.test.ts`, `tests/browser/reliability.spec.ts`, `scripts/reliability-profile.mjs`, `package.json`, this report. Phase 14 contributes run configuration and save integration.

Why the approach is maintainable: Graphics changes presentation, not authoritative collision/damage/entity budgets. One profile function maps settings to pixel density/effect density. Automatic adjustment is a small pure controller with bounded state and no timer. Diagnostics retain 240 timing samples. The same existing renderer/lifecycle is used in stress and fallback tests. The long-session script explicitly identifies injected targets and above-production actor budgets instead of calling them a real survival run. No new dependencies or speculative collision subsystem were introduced.

Tests run: Graphics tests cover DPI/resolution independence, hardware defaults, sustained-frame adaptation, hysteresis, suspension/invalid samples, very slow-frame recovery and bounded metrics. Challenge tests cover opening-enemy speed, all field-healing paths, once-only actual kill metadata and precise endless transition time. Complete unit/type/build and browser outcomes are recorded in [the combined report](PHASES_10_14_REPORT.md).

Browser smoke steps: The reliability suite checks saved controls, changing presets while paused without clock advancement, native capture recovery, and audio preference preservation when storage is denied. Ten real restarts compare every scene resource count against the initialized title baseline, check zero remaining sprite managers, zero audio voices/errors and reuse of the three-node audio graph, then request Chrome GC for a retained-heap comparison. Babylon's single scene-owned default material is warmed before measurement; every run returns to that exact baseline with no meshes, geometry, textures, sprite managers, transforms or lights. Retained Chrome heap is 28.05MB before asset warmup and 32.61MB after ten restarts/GC. Restart also clears an injected previous encounter warning. A separate real scene renders 210 enemies, a leader plus six followers and up to 220 projectiles; injected actors deliberately exceed the normal 190-enemy/six-total-party budgets. Missing native and fallback artwork requests are aborted to verify a ready generated character, movement and no page errors. Final suite: **3/3 passed**. Evidence: `artifacts/performance/browser-restarts.json`, `browser-crowd.json`, `crowd.png` and `artifacts/browser/13-final-lifecycle`.

Known limitations: Chrome tests use SwiftShader software WebGL. Their frame intervals are diagnostic evidence for that renderer, not integrated-GPU or gaming-GPU FPS. No thirty-minute wall-clock rendered endurance or subjective human comfort claim is made. The thirty-minute simulation and ten real rendered restarts test complementary lifecycle/state paths. Optional heap data is Chrome-specific; explicit engine resource counts are portable. Existing large Babylon bundle size remains a packaging concern. Additional device profiling is needed before promising a minimum FPS across hardware.

Balance / performance impact: No automatic entity removal, damage scaling or difficulty changes. The reproducible `npm run profile:reliability` completed **1,800 actual endless simulation seconds / 54,000 updates** with **210 stationary non-retaliating enemies, seven party actors, 220 projectiles and up to 165 drops**. It took 21.47 seconds on this host. Sampled simulation CPU median was **0.356ms**, p95 **0.758ms**, maximum **6.858ms**. GC-retained heap was 9.71MB before warmup, 10.54MB at five minutes and 10.57MB after thirty minutes. Status ownership stayed at 60, with no state/cap assertions failing. Projectile scans were the largest measured simulation portion at **0.304ms/update**; that absolute cost did not justify adding a spatial partition. Evidence and conditions: `artifacts/performance/endless-profile.json`. This fixture does not measure survival or target GPU performance.

Next recommended phase: 14, implemented alongside these changes; then phase 15 after human balance/comfort review and device measurements.
